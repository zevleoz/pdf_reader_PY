Where the workflow breaks

The main usability issue is task continuity. The same student has a profiling record, an M1 hub and a meeting page, each with its own idea of what should happen next. Review and export then cross another boundary between the report editor and the printable document.

Find

Profiling → M1

The profiling student tab links into a separate platform. The profiling progress tracker and workbench do not surface open M1 work.

Resume

Roster → Student → Meeting

The roster can say 核对发布. The same student’s hub can say 直接创建教案. Choosing the row or its action changes the task.

Review

Transcript → Parent report

Staff review speakers, verify evidence and modify the report. The page puts a fixed-width print document inside the editing workspace.

Deliver

Teaching plan → Family copy

A mentor can start from a report draft or create a standalone plan. The internal plan, individual session PDF and confirmed parent plan serve different audiences.

How M1 got here

  1. Original M1

    100711e introduced preparation for the First Meeting. The 5 November redesign centered the work on one student and split meeting preparation from post-meeting reporting.

  2. 10–14 Nov

    Development planning added mentor approval and a parent edition. The workflow later allowed planning from the report’s AI draft, so publication became a handoff milestone while planning could begin earlier.

  3. 17–20 Nov

    Standalone plans, co-mentor assignments and a student-scoped hub made access and teaching more flexible. DP16 added an explicit save-and-snapshot barrier to the single-session internal PDF.

  4. 21 Nov baseline

    The profiling React shell and M1’s Flask pages both ship in this checkout. The student entry, task resume, report editor and family delivery now need a shared contract across those pages.

P0M1-01 · Report handoff

Owner · Report engineering

Export and publication can outrun the report editor

The report preview saves edits from inside an iframe when a field loses focus. The surrounding page gives 导出 PDF a direct print link and posts 正式发布 without waiting for that iframe’s save queue. Under a slow write, the print view can open the prior saved copy while staff can still see their new text in the editor. The same delay let publication return HTTP 200 before the write. The write then returned HTTP 409 and the edit was absent from the published report.

Change. Put dirty, saving, failed and saved states beside the action. Flush both editor and page changes before export, publication or reopening. Require the reviewed revision and version on publication, and render the committed snapshot for export. Reuse the DP16 session export pattern and keep one visible save state.

Pass when a delayed edit appears in the resulting print snapshot and published report, or the action halts with the unsaved edit intact and a retry. A second tab changing the revision requires fresh review before publication.

Iframe editor queue and blur handling (lines 119–149, 208–223) · Outer publish handler (1491–1500) · DP16 revision-pinned print (1177–1238)

P1M1-02 · Student navigation

Owners · Product and M1 engineering

Three pages disagree about the same student’s next action

In Chrome, the profiling student record led to a hub headed by 直接创建教案 for a student with a generated report awaiting review. The roster and meeting page showed 核对发布. Once any plan exists, the roster’s resolver can favor it over the report, and 有待办 uses the latest plan’s export status even for rows without a next-action button. After a report draft exists, the plan list allows report-based creation, while the meeting header waits for publication to offer it as the primary action.

Change. Give each student one canonical hub and one permission-aware task summary. Show open work per document with its owner, status and exact resume link. Rank the recommended action by the user’s role and actual work state. Offer both plan creation modes when eligible. Give profiling a small M1 task summary and a same-student return link.

Pass when roster, hub, meeting and profiling surface the same actionable report task for its owner. A completed plan cannot hide an open report. A co-mentor sees 查看会后报告（只读） plus the editing actions they can actually take.

Roster next action and completion (477–522, 571–603) · Hub action (106–134) · Meeting action (101–166) · Profiling entry (355–358, 420–428)

P1M1-03 · First Meeting

Owners · Product design and M1 engineering

“New First Meeting” can return to the page you just left

The hub’s 新建 First Meeting link goes to /m1?student=…. When that student is already on the roster, the page redirects to the same hub before opening the creation dialog. Chrome reproduced the round trip. From the roster, 添加学生 sounds like roster management even though it creates a meeting for an existing student. The picker disables anyone with any prep, while the creation endpoint reuses a non-final prep and can create a prep after the old one is final. The interface leaves the policy unresolved.

Change. Separate “show student” from “start or resume meeting” at the route and API level. Use 新建首次会议 or 继续会前准备 with the student already selected. For an incomplete Y4, show the reason and link to the student’s Y4 area. Have Product confirm whether a second meeting is required, then apply that rule to the picker, hub and endpoint.

Pass when an eligible student already on the roster can reach the correct form in one click. Test no meeting, open preparation, final preparation and incomplete Y4. Every case ends at a form, an existing task or an explanation with a destination.

Hub link (43–49) · Picker and roster redirect (291–292, 450–467) · Server creation rules (643–675)

P1M1-04 · Recovery

Owners · Backend and frontend platform

A blank roster and a stuck generation leave staff without a recovery path

The roster starts at zero with an empty list. A failed roster request has no handler that replaces it with an error and retry. Failure of the student picker request is converted into an empty list. In meeting preparation, the active job ID is stored in the initiating tab’s session storage, and boot only resumes polling if there is no existing draft. One failed poll stops scheduling further status checks. The report and plan screens use different discovery and recovery mechanisms.

Change. Render loading, empty, inaccessible and retryable error states in the page. Persist an active job reference with each document, preserve the previous draft and use a bounded retry policy. Put retry and support context beside the status. Persist idempotency keys for job start and fence off stale workers before retrying.

Pass when a 503 explains how to retry, and an active job resumes from another tab or device after a transient disconnect. A worker death reaches a recoverable state and retry starts a single new attempt.

Roster loading (450–468) · Preparation polling (581–647, 1225–1236) · Plan job discovery (972–989)

P1M1-05 · Keyboard

Owners · Frontend and accessibility QA

Keyboard users can miss the transcript upload and leave an open dialog by tabbing

The initial transcript picker shows 选择文件 as a styled span inside a label with a hidden input. The supplementary upload uses a styled span inside a div. Both lack a focusable upload control in the rendered DOM. Pasting is an alternative for transcript text. The Add Student dialog moves focus in and restores it on Escape, but Shift+Tab from its close button reached the page behind it. Roster status filters declare a tab list around ordinary buttons and expose no selected state as tabs.

Change. Use keyboard-operable file pickers with a persistent accepted-formats label and inline errors. Put dialogs on a shared modal implementation with contained focus and predictable escape. Render roster status controls as a labeled group of pressed-state filter buttons.

Pass when a keyboard-only mentor can select a transcript and additional file, complete and dismiss both creation dialogs, use filters and recover an error. Verify with VoiceOver and NVDA on the supported browser combinations.

Report file controls (31–58) · Roster filters and dialog (18–55) · WCAG 2.2 Keyboard · W3C modal pattern

P1M1-06 · Report review

Owners · Product design and report engineering

Review asks staff to work inside the print layout

The report uses a fixed-width A4 sheet inside a scrollable iframe. At 375 px, the document measured 794 px inside a 375 px editing frame, while the outer page fit the viewport. 需要补全 in the outer page gives a count and points to yellow boxes. Field-by-field navigation lives inside the preview toolbar, while speaker review and publication live outside it. A reviewer has to switch between two sets of controls and two scroll positions to finish one task.

Change. Make section editing responsive and keep the A4 renderer for preview and printing. Put a single issue index above the editor. Each blocking item should name the issue and focus the affected field. Show the transcript excerpt, speaker status and report text together where they are needed. Support phone triage and review, and explicitly define any desktop-only authoring scope.

Pass when a mentor can locate and resolve an issue, find the save outcome and reach the next issue at 375 px and at 200% zoom. Test reflow at 320 CSS px for the editing interface and preserve the printed page format.

Fixed sheet width (57–65) · Issue summary and preview (696–703, 766–775) · In-frame issue navigation (54–116) · WCAG 2.2 Reflow

P1M1-07 · Status and audience

Owners · Product operations and frontend

Workflow labels hide what happened and what’s safe to hand over

The meeting track marks First Meeting complete from the date alone, including today, while the roster puts today’s dates with upcoming meetings. The student hub can show prep as 待生成 even when its roster has AI 初稿 · 待定稿. The report screen uses 正式发布, then a separate PDF action. Its publish operation updates report state and records an audit event, so the label alone does not tell staff whether anyone received a copy.

Change. Use explicit facts for meeting completion, document readiness and delivery. Label the artifact and audience at each handoff 内部教案（单节）, 报告草稿（内部审阅）, 正式报告（家长）, and 家长版发展计划. Explain that staff share the family PDF separately if that remains the delivery model. Put “read only” and the expected owner beside the unavailable action.

Pass when staff can distinguish scheduled, held, approved, exported and shared states and choose the intended artifact without guessing. Dry-run the handoff with an admin, primary mentor and co-mentor.

Meeting track (213–230) · Hub meeting card (404–429) · Publish operation (698–718) · Report handoff actions (108–121)

Define actions on the server

Extend the student overview with each document’s current state, revision, owner, permissions, prerequisites and resume link. Calculate open work across relevant meetings and plan blocks. Have all entry points render the same action objects. A standalone plan stays valid without a meeting. M1 work can appear on the profiling workbench without becoming a required stage for all students.

Make every delivery revision-specific

Extend the save-and-print pattern already used for single-session plans. Keep drafts editable and retain a committed version with actor, audience and timestamp for each final output. Keep current access rules for record, source and print routes. Serve family deliverables from a confirmed snapshot and make an outdated parent version visible after internal changes.

Give background work a durable record

Use a database-backed job record scoped to document, operation and attempt. Store the prior revision and latest progress on the server. Return that reference from detail APIs so a new browser can resume. Continue using the existing subprocess workers on the current host, with bounded retries, lease expiry or heartbeat reconciliation, and clear failure messages.

Use one review surface

Put blocking items, speaker checks, evidence and editable sections in one responsive workflow. Preserve the printable document and provide explicit printable preview. Give the main action an audience and save state. Reuse accessible React primitives where applicable and implement equivalent behavior in the Flask pages.

Product decisions before implementation. Confirm whether a second First Meeting is valid, which staff role owns meeting completion, and whether the site should record manual family handoff. Confirm which authoring tasks staff need to complete on a phone. Keep advisory AI checks, human review and export permissions aligned with the agreed policy.

Release sequence and gates

Implementation update. The M1 release is based on cd49556. It binds publication and PDF export to the saved revision, gives staff a shared next action across Profiling and M1, adds explicit roster and upload retries, and opens report review in a responsive section editor.

Fresh sessions can resume preparation, report, and plan generation. A timed-out attempt preserves the previous draft and cannot write after a retry has taken over. The web process and generation workers must share the existing persistent data/_m1_jobs directory.

The candidate retains one First Meeting per student. An elapsed scheduled date reads as awaiting confirmation, and staff send the official family PDF after downloading it.

Local verification. The frontend build succeeded and the repository suite finished with 2,791 passed and 13 skipped. Chrome verified the Profiling handoff, generation recovery after a transient error, and keyboard review from required issue to speaker evidence and saved PDF at phone widths of 320 and 375 CSS pixels. Staging and the staff pilot are pending.

Suggested owners are roles. Assign a named owner and verification date to each gate before scheduling a rollout.

Scenarios for acceptance

  • Admin. Starting in profiling, find a student with complete Y4, schedule or resume First Meeting, find open prep/report work, and assign or revoke a co-mentor. Switch to a second student to test that context and permissions follow the selected record.
  • Primary mentor. Prepare and finalize the meeting document. Upload or paste a transcript, check attribution and evidence, make a final edit, and publish and export the exact reviewed revision. Create a report-based development plan from a draft and an independent plan where applicable. Approve the internal version, export a single session, then confirm and export the family copy.
  • Co-mentor. Find the assigned student under 我参与的, open shared source and report pages, and collaborate on the development plan. Confirm that read-only actions are intelligible and that revocation takes effect in an open tab and on direct links.
  • Viewer and out-of-scope advisor. Verify that profiling entry points and direct M1 links respect access. A denied document does not expose its title, source material or PDF.
  • Interrupted or concurrent work. Retry a roster 503, rejoin generation in a fresh tab, recover a failed save without losing the text, and resolve a second-editor revision conflict. Use Chrome and Safari at supported widths, then repeat core tasks with keyboard and assistive technology.

Proposed pilot targets. Zero incorrect or stale family exports, zero lost edits in save and retry checks, zero dead-end primary actions, and completion of every role scenario. Track elapsed time from student selection to the intended task and use the pilot to set a time target. Log stage, result, duration and error category without transcript or report text.
