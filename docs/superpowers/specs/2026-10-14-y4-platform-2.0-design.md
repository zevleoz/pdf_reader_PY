# Y4 平台 2.0 设计 Spec

日期：2026-10-14
状态：已与需求方确认设计方向（见「已确认决策」）

## 1. 背景与目标

### 1.1 现状（1.0）

凭远教育 Y4 综合测评内部系统：咨询师上传学生从外部测评平台导出的 4 份 PDF 子报告（A2 核心素养 / B3 核心学习能力 / B4 核心认知能力和成长型思维 / B6 职业发展），系统用视觉大模型提取 124 项结构化指标（schema_124），渲染 v1/v2 两版综合评估 PDF，数据落库形成学生档案。

- 技术栈：Flask 3 + Jinja2 服务端模板 + 无依赖 vanilla JS；SQLite（默认 `data/y4_students.db`）/ PostgreSQL（`DATABASE_URL`）；SQLAlchemy 2.0 declarative + 手写迁移（`db.py`）
- 部署：阿里云 ECS 2核2G，gunicorn（unix socket，max_requests=10，异步生成作业必须 fork 子进程），nginx + Let's Encrypt，**对外必须走 Cloudflare Tunnel**
- 用户：单一管理员密码（`ADMIN_PASSWORD` env），Flask session `is_admin`，无角色、无用户表
- 学生身份：纯姓名匹配（`find_or_create_student`），无唯一 ID

### 1.2 2.0 目标

1. 定位升级：从"报告转换工具"升级为 **Y4 平台管理系统** —— 学生 profiling 数据中心（Y4 四维 + 附加问卷 + 未来更多测评）
2. 从单用户走向多角色 client-facing：公司其他部门可查阅/调用数据，顾问可管理自己的学生
3. 新功能：附加问卷系统 —— Y4 完成后自动识别该生需要的附加问卷 → 人工确认 → 一次性链接 / 临时账号分发 → 学生在线作答 → 原始答案回写同一学生档案库

### 1.3 已确认决策（需求方逐条选定，不得擅自变更）

| # | 问题 | 决策 |
|---|---|---|
| 1 | 问卷形态 | 系统内自建问卷填写页面 |
| 2 | 引擎灵活度 | 固定题库（开发时配好），数据结构预留扩展 |
| 3 | 识别逻辑 | 规则引擎自动推荐 + 人工确认后才发送 |
| 4 | 学生入口 | 一次性链接 + 临时账号双制 |
| 5 | 角色体系 | Admin / Advisor / Viewer 三角色 |
| 6 | 结果整合深度 | 只存原始答案（JSON），档案页展示；不计分、不并入 124 指标 |
| 7 | 前端技术 | 保留 Flask 后端；管理端 Tailwind + Alpine.js（CDN 引入，无 Node 构建链） |
| 8 | 链接送达 | 系统生成，顾问一键复制，微信手动发送；不做自动通知 |
| 9 | 现有模块 | 全部保留，重新分组进新导航 |

## 3. 角色与权限

### 3.1 三角色

| 角色 | 说明 | 权限 |
|---|---|---|
| Admin | 系统管理员（需求方本人） | 全部权限 + 用户管理 + 题库管理 + 规则管理 |
| Advisor | 顾问 | 自己名下学生（`students.advisor_name` 匹配）的档案/报告查看与生成、问卷任务确认与分发、预约/纪要相关操作 |
| Viewer | 其他部门查阅者 | 全站只读：学生画像、报告查看、Dashboard、导出查看；无任何写操作、无用户管理、无规则配置 |

### 3.3 认证与授权机制

- 登录页 `/login` 改为账号 + 密码表单；成功后 session 写入 `user_id` / `role` / `advisor_name`
- 旧 `is_admin` session 标记废弃；为兼容平滑过渡，装饰器统一重写为：
  - `@login_required` — 任何已登录用户
  - `@role_required('admin')` / `@role_required('admin','advisor')` 等
  - Advisor 数据隔离通过查询层实现：凡按学生列表/档案/报告/问卷任务查询，role=advisor 时自动附加 `students.advisor_name = current_user.advisor_name` 过滤
- 登录接口加限流：同一 IP 5 次/分钟，失败计数超限返回 429（沿用 `app.py` 现有滑动窗口限流工具的模式）
- 保留旧 `ADMIN_PASSWORD` 环境变量读取但仅作迁移期回退：若 users 表为空且请求带旧密码，提示"系统已升级，请使用账号登录"并拒绝（不自动放行）
- 公开面（无需登录）：`/` 落地页、`/booking`、`/q/<token>`、`/student/login` + 学生端会话、`/api/docs`、`/api/v1/*`（Bearer token 鉴权不变）

### 5.4 学生管线双视图（2026-10-17 流程裁决）

「待办优先级」与「生命周期进度」拆成两套语义，不再共用一套阶段顺序：

| 视图 | 位置 | 语义 | 顺序 |
|---|---|---|---|
| 待办优先级 | `/students` 阶段栏、`/workspace` 最近活跃学生 | 现在先处理谁 | `pending_approval → awaiting_student → awaiting_report → booked → reported → ready` |
| 生命周期进度 | 学生 360° 顶部 stepper | 学生走到哪 | `booked → report → minutes → pending_approval → awaiting_student → ready` |

三条固化裁决：

1. **Six A.M. 是报告后的后台更新**：不占 stepper 节点，也不阻塞“报告已生成”状态；报告落库、任务标记完成后才跑 6AM 档案，失败只记日志。360° 页在有报告但档案未落库时显示「后台更新中」chip，落库后显示「已更新 · v{version}」。
2. **会议纪要只是非强制进度节点**：没有纪要时不阻塞问卷；一旦存在问卷任务或纪要，生命周期继续前进。stepper 上该节点带「可选」badge。
3. **当前有效问卷 `submitted` 后即“已就绪”**：历史 `expired/rejected` 不阻塞，但若没有更新的 `submitted`，仍需回到问卷处理（`pending_approval`）。

实现落在 `pipeline.py`：`compute_stages()` 服务待办优先级，`compute_progress(student_id)` 服务生命周期进度；均为纯查询层推导，零 schema 变更。

## 6. 问卷子系统（本期最大新增）

### 6.1 数据流（端到端）

```
POST /api/generate/result 成功落库（_save_report_to_db 完成）
  → 触发问卷识别钩子（异步、失败不影响报告主流程）
  → 规则引擎按 published 规则评估该生 schema_124
  → 命中即创建 assignment(status='pending')，每生每问卷去重（未完成过的不再推荐）
  → 工作台/问卷中心出现「待确认」任务
  → admin/advisor 确认（可增删问卷、选择分发方式）→ status='sent'
      分发方式：
      a) 一次性链接：创建 assignment_token(token, expires_at=7天) → URL /q/<token>
      b) 临时账号：创建/复用 student_account(username, password) → URL /student/login
  → 顾问复制链接/账号，微信发送（系统不做通知）
  → 学生作答：
      a) /q/<token>：免登录，直达该问卷，提交后 token 作废
      b) /student/login：登录后看待办问卷列表，逐份作答，支持进度保存（draft）
  → 提交：response 落库（原始答案 JSON），assignment.status='submitted'
  → 学生档案页「问卷」tab 可见；问卷中心任务列表更新
  → 过期：token 超 7 天未提交 → status='expired'（可重新生成链接复活）
```

### 6.3 问卷 schema_json 格式（题库题目定义）

```json
{
  "version": 1,
  "questions": [
    {
      "id": "q1",
      "type": "single | multi | scale | text",
      "title": "题目文字",
      "required": true,
      "options": [{"value": "a", "label": "选项A"}],
      "scale": {"min": 1, "max": 5, "min_label": "完全不符合", "max_label": "完全符合"},
      "max_length": 500
    }
  ]
}
```

- `single`/`multi` 必须有 options；`scale` 必须有 scale 区间；`text` 可有 max_length
- 第一期不支持跳题逻辑（字段预留 `visible_if`，引擎暂不实现）
- 题库 seed：固定题库以 JSON 文件放 `PDF_converter/questionnaires_seed/`（每问卷一个文件），启动时 upsert 入库；Admin 可在题库页启停问卷，但不能在线编辑题目（编辑=改 seed 文件）

### 6.4 识别规则 rules_json 格式（DSL）

```json
{
  "version": 1,
  "rules": [
    {
      "questionnaire_code": "Q-MOTIV-01",
      "when": {
        "all": [
          {"code": "085", "op": "<=", "value": 40},
          {"code": "091", "op": "in", "value": ["低", "较低"]}
        ]
      },
      "reason": "学习动机指标偏低，建议补充学习动机量表"
    }
  ]
}
```

- 条件对象：`{code, op, value}`；op ∈ `=, !=, <, <=, >, >=, in, contains`
- `all`（且）/ `any`（或）二选一，第一期不支持嵌套
- `code` 引用 schema_124 的指标 code；value 与指标 value 类型对齐（数值比较前尝试 float 转换，失败则字符串比较）
- 引擎实现位置：`PDF_converter/questionnaire_engine/` 新包，参照 `six_am/` 的模块纪律（纯函数、不导入 Flask、不直接访问 DB；输入 schema_124 列表 + rules_json，输出命中列表 `[{questionnaire_code, reason}]`）
- 触发点：`_save_report_to_db` 完成后调用（try/except 包裹，异常只记日志）；评估用 published 版规则；无 published 版则跳过

### 6.5 状态机

```
pending（待确认） --确认--> sent（已发送） --提交--> submitted（已完成）
   |                            |
   +--驳回--> rejected          +--token 过期--> expired --重新生成链接--> sent
```

- 同一 (student_id, questionnaire_id) 只允许一条活动任务（pending/sent）
- expired/rejected 后可再次推荐或手动新建

### 6.6 学生端页面（公开面，无管理端 UI 框架）

- `/q/<token>`：独立轻量页面（品牌化、移动端友好），展示问卷说明 + 题目 + 提交；token 无效/已用/过期显示对应友好文案
- `/student/login` + `/student/home`：学生登录后看待办问卷列表 + 已完成记录；作答支持保存草稿
- 学生端 session 与管理端 session 分离（不同 session key），学生账号无任何管理端权限
- 提交即写 responses + 更新 assignment；重复提交防护（提交后 assignment 已 submitted 则拒绝）

### 6.7 问卷中心管理页

- **任务列表**：状态筛选 tab（待确认/已发送/已完成/已过期/已驳回）；行内操作：确认（选分发方式、生成链接/账号、一键复制）、驳回、重新生成链接、查看答案
- **题库**：问卷列表、题目预览、启停
- **识别规则**：版本列表（draft/published/archived）、新建 draft（JSON 编辑器 + 语法校验 + 用任一学生的 schema_124 试算预览命中）、发布（自动归档旧 published）

## 7. 技术架构

### 7.1 app.py 拆分（Agent A）

现状 `app.py` 4934 行单文件。拆为：

```
PDF_converter/
```
