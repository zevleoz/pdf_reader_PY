# 解读会纪要与学生档案关联改造计划

## 一、仓库研究结论

### 1.1 现有架构梳理

**数据库层 ([db.py](file:///Users/jefflau/projects/pdf_report_converter/PDF_converter/db.py))**
- 4 张表：`students`（学生）、`reports`（报告，含 `data_json` 存完整测评数据和 `interpretation` 存 AI 解读）、`bookings`（预约）、`availability`（可预约时段）
- 学生与报告是 1:N 关系（`reports.student_id → students.id`）
- `_migrate_schema()` 支持渐进式列迁移（SQLite 专属）

**后端路由 ([app.py](file:///Users/jefflau/projects/pdf_report_converter/PDF_converter/app.py))**
- 页面路由：`/transcript`（解读会纪要页，需登录）、`/students`（学生档案页，需登录）
- API 路由：
  - `POST /api/transcript` → 读取 `prompts/transcript_summary.md` 作为 prompt，当前硬编码读 `data/report_data.json` 取测评数据（只对应"当前会话"的报告）
  - `POST /api/transcript/docx` → 调用 `_build_docx()` 生成格式丰富的 Word 文档（红色标题、居中学生信息表、•/☐/☑ 复选框、页脚 `凭远教育 · Y4 综合测评系统`）
  - `GET /api/students`、`GET /api/students/<id>/reports` 已存在
  - `GET /api/reports/<id>/raw` → 返回报告完整 raw data（已可用）
- 所有敏感路由均已加 `@admin_required` 或 `@page_login_required`

**学生档案页 ([templates/students.html](file:///Users/jefflau/projects/pdf_report_converter/PDF_converter/templates/students.html))**
- 学生列表：每行有「查看报告」「删除」操作
- 报告列表：每个报告有「AI 解读」「原始数据」「下载 JSON」「删除」操作
- 目前没有任何跳转到解读会纪要的入口

**解读会纪要页 ([templates/transcript.html](file:///Users/jefflau/projects/pdf_report_converter/PDF_converter/templates/transcript.html))**
- 手动输入 学生姓名 / 年级 / 性别
- 支持 URL 参数 `?name=X&grade=Y` 预填（但没有 `student_id` 关联）
- 上传/粘贴逐字稿 → 调 `/api/transcript` → 渲染 Markdown 结果
- 下载选项：复制 / TXT / **DOCX**（DOCX 已有精美排版，符合「方便阅读」需求）
- Session 级持久化（`sessionStorage`）存逐字稿和结果
- **关键缺陷**：后端读 `DATA_DIR/report_data.json`（全局文件），无法对应到"某学生的某份报告"

**Prompt 模板 ([prompts/transcript_summary.md](file:///Users/jefflau/projects/pdf_report_converter/PDF_converter/prompts/transcript_summary.md))**
- 已定义严格的五段式结构：核心发现(3条) → 四维测评要点 → 家长反馈 → 行动清单(含负责人/期限/预期效果) → 下次复盘
- 总字数 500-800 字
- 与项目记忆中「会议纪要硬规则」完全一致

### 1.2 当前痛点

| 痛点 | 影响 |
|------|------|
| 纪要页与学生档案无关联 | 需手动重填学生信息，无法自动带入选定报告的测评数据 |

| 无 prompt 配置注入点 | 用户无法指定自定义 prompt |

## 三、具体改动步骤

### 步骤 1：数据库层（db.py）——新增 MeetingMinutes 表

1. 新增 ORM 类 `MeetingMinutes`：
   - `id` (PK)
   - `student_id` (FK → students.id, **非空**)
   - `report_id` (FK → reports.id, 可空 — 允许不绑定特定报告的纪要)
   - `transcript_text` (Text, 原始逐字稿)
   - `minutes_text` (Text, AI 生成的纪要)
   - `created_at` (DateTime)
   - `updated_at` (DateTime)

2. `_migrate_schema()` 中加迁移逻辑：`PRAGMA table_info(meeting_minutes)` → 不存在则 `CREATE TABLE`（兼容已有 DB）

3. 新增 CRUD 函数：
   - `add_minutes(student_id, report_id, transcript_text, minutes_text) -> int`
   - `get_minutes_by_student(student_id) -> List[Dict]`（按创建时间倒序）
   - `get_minutes_by_report(report_id) -> List[Dict]`
   - `get_minutes(minutes_id) -> Optional[Dict]`
   - `update_minutes(minutes_id, **fields)`（支持重新生成后覆盖）
   - `delete_minutes(minutes_id)`

### 步骤 2：后端路由（app.py）

#### 2.1 改造 `POST /api/transcript`（**关键**）
- 入参新增可选字段：`student_id` (int)、`report_id` (int)、`custom_prompt` (str, 用户自定义 prompt 全文，可选覆盖 `transcript_summary.md`)
- **测评数据上下文获取逻辑变更**：
  - 若传了 `report_id` → 调 `_db.get_report_raw(report_id)` 取 `raw` 数据生成 `report_summary`（不再读 `report_data.json`）
  - 若只传了 `student_id` 未传 `report_id` → 取该学生最新一份报告的 raw data
  - 都没传 → 保持旧逻辑（读 `report_data.json`，兼容手动生成流程）
- 自动带学生信息：
  - 从 report/student 记录取 `name / grade / gender` 覆盖空入参
- **Prompt 逻辑**：
  - 优先用 `custom_prompt`（如果用户在前端提供了自定义 prompt 文本）
  - 否则读 `prompts/transcript_summary.md`
  - 做变量替换 `{student_name}` `{report_summary}` `{transcript}`
- 生成纪要后，如果有 `student_id`，自动入库调用 `_db.add_minutes()`，返回 `minutes_id`

#### 2.2 新增纪要管理 API
- `GET /api/students/<student_id>/minutes` → 返回该学生所有历史纪要（含对应报告日期）
- `GET /api/minutes/<minutes_id>` → 返回单条纪要详情（逐字稿+纪要+关联信息）
- `PUT /api/minutes/<minutes_id>` → 更新（重新生成/手动修改）
- `DELETE /api/minutes/<minutes_id>` → 删除
- 全部加 `@admin_required`

#### 2.3 改造 `POST /api/transcript/docx`
- 入参新增可选 `minutes_id` → 直接从 DB 取 `minutes_text` 和学生信息生成 DOCX（便于从学生档案一键下载）
- 无 `minutes_id` 时保持旧逻辑（前端传 summary + student 信息）

### 步骤 5：Prompt 模板替换 + 后端 Prompt 组装逻辑适配

**用户已提供自定义 prompt 全文（见附录 A），此步骤作为步骤 0 优先执行。**

#### 5.1 替换 `prompts/transcript_summary.md`
- 直接把附录 A 的 prompt 全文写入该文件（覆盖现有内容）
- 新 prompt **不使用** `{student_name}` `{report_summary}` `{transcript}` 模板占位符，而是写成一个完整的 system prompt

#### 5.2 适配后端 `POST /api/transcript` 的 Prompt 组装逻辑（关键改动）
旧逻辑（废弃）：读 prompt 文件 → `.replace()` 替换三个占位符 → 作为 system_content

新逻辑（采用）：
- 读 prompt 文件 → 作为**完整的 system prompt**，不做任何字符串替换
- 在 user message 中**拼接**所有动态上下文：
  ```
  messages = [
    {"role": "system", "content": prompt全文（用户已给）},
    {"role": "user", "content":
      "## 学生基本信息\n"
      "姓名：{student_name}\n年级：{student_grade}\n性别：{student_gender}\n\n"
      "## Y4 测评数据摘要（供交叉验证参考）\n"
      "{report_summary}\n\n"
      "## 解读会录音转写/会议纪要\n"
      "{transcript}\n\n"
      "请基于以上提供的录音转写/会议纪要，直接生成最终会议记录。"
    }
  ]
  ```
- 原因：用户 prompt 的最后一句明确写了「现在请基于我接下来提供的录音转写/会议纪要，直接生成最终会议记录」，所以所有动态数据应该放在 user message 里，而不是替换 system prompt 的占位符

#### 5.3 前端「自定义 Prompt」面板功能保留
- 功能不变：用户在前端粘贴新 prompt 会通过 `custom_prompt` 覆盖服务端默认
- 同样采用新的组装逻辑：custom_prompt 作为 system，上下文拼在 user message

## 五、依赖与注意事项

### 5.1 不触碰的代码（硬约束）
- PDF 生成流水线（`extract.py` / `validate.py` / `generate.py`）**不修改**
- AI 解读相关（`reports.interpretation` 列和 `/api/reports/<id>/interpret`）**不修改**
- 已有的 DOCX 生成函数 `_build_docx()` **仅扩展入参，不改排版逻辑**

### 5.2 鉴权约束（硬约束）
- 所有新增 API 路由和页面路由必须带 `@admin_required` / `@page_login_required`
- `/transcript` 页面已有 `@page_login_required`，保持
- 新增的 `/api/students/<id>/minutes` 等接口全加 `@admin_required`

### 5.3 Prompt 注入安全与格式
- 前端传 `custom_prompt` 时服务端直接作为 **system prompt** 使用（admin 身份，无需 HTML 转义级别防护）
- 所有动态上下文（学生姓名/报告摘要/逐字稿）统一在 **user message** 中拼接，不修改 system prompt 本身
- 不做任何 `{xxx}` 占位符替换 → 不存在「占位符缺失导致 AI 输出空内容」的风险

### 5.4 DOCX 渲染器与新输出结构的兼容性
用户新 prompt 的输出使用 `# / ## / ###` Markdown 标题（七段式结构），而 `_build_docx()` 目前只识别 `**一、xxx**` 这种加粗标题格式。

**必须**扩展 `_build_docx()` 以支持：
- `# 标题文字` → Word 的 Heading 1（红色 16pt 加粗）
- `## 标题文字` → Heading 2（深红 14pt 加粗）
- `### 标题文字` → Heading 3（深色 12pt 加粗）
- 原有 `**一、xxx**` 格式保留（向后兼容）

同理，`renderMinutesMarkdown()` 也要在现有基础上补全 `# / ## / ###` 的处理规则。

### 5.5 兼容性
- 不传 `student_id/report_id` 时行为与旧版一致（兼容老用户手动使用场景）
- SQLite 迁移逻辑幂等（重复启动不报错）
- PostgreSQL 模式：`_migrate_schema` skip SQLite 专属逻辑，但 `Base.metadata.create_all(engine)` 会自动建 `meeting_minutes` 新表（无历史数据问题）

### 5.6 AI 模型选择
- 纪要生成应**优先**读 `ITERATION_MODEL` 环境变量（项目记忆：qwen-turbo 速度优先），避免 API 超时
- 后备顺序：`ITERATION_MODEL` → `AI_TEXT_MODEL` → `qwen-turbo`（默认不再是 qwen-plus，降低延迟风险）
- max_tokens 调至 8192（新 prompt 输出结构比旧纪要更详实），timeout 保持 180 秒

### 5.7 输出标题占位符替换
用户 prompt 规定最终输出开头必须为 `# Y4测评解读会议记录｜【学生姓名】`，AI 可能写成字面的 `【学生姓名】` 而不是实际名字。

因此在**服务端**调用 AI 得到 `summary` 后，入库前做一次兜底字符串替换：
- `summary.replace("【学生姓名】", student_name or "")`
- 若 student_name 为空则不替换，留给人工补全

# 一、总体原则

## 1. 只基于会议内容，不自行补充

所有结论必须能够在录音/会议纪要中找到依据。

可以对会议中分散出现的内容进行**归纳、整合和逻辑串联**，但不能：

* 自行添加录音中没有提到的学生特点
* 根据常识推测学生可能存在的问题
* 根据Y4报告数据自行进行新的心理学解释
* 自行诊断学生
* 自行增加会议中没有讨论过的建议
* 为了让报告完整而"脑补"缺失信息

如果某个维度会议中没有讨论，就不要强行补充。

---

## 2. 不要机械复述Y4报告数据

会议记录的价值不是把报告重新抄一遍。

不要大量写：

> "情绪稳定性34分，同龄平均40分……"

而应该提炼为：

> "Brian整体情绪状态较稳定，但在自我能力评价方面存在一定的不确定性，对自己的学校表现也较为苛刻。"

**数据只在能够帮助解释会议结论时保留。**

如果某个数字是会议讨论的重要依据，可以保留；如果只是普通报告数据，则优先转化为结论。

---

## 3. 重点提炼"比报告数据高一层"的内容

尤其关注以下四类信息：

### A. 解读老师形成的判断

例如：

* 这个数据意味着学生可能存在什么状态
* 某两个维度之间有什么联系
* 哪个问题是当前真正需要关注的
* 哪些看似是问题的地方其实不是问题
* 哪些优势可以成为后续成长的基础

### B. 家长对学生真实情况的反馈

例如：

* 家长是否认可测评结果
* 家长补充了什么实际案例
* 学生在学校、家庭、社交、学习中的真实表现
* 家长对孩子的观察与测评是否吻合

### C. 测评结果与现实情况之间的交叉验证

这是会议记录非常重要的内容。

例如：

> 测评显示同伴关系整体安全，但信任和沟通程度相对有限；家长反馈学生目前在德国尚未找到真正交心的朋友，两者相互印证。

要优先保留这种**"测评发现 → 家长反馈 → 得到验证"**的内容。

### D. 会议最终形成的成长方向

例如：

* 当前最需要提升什么
* 为什么需要提升
* 应该通过什么方式改善
* 哪些事情暂时不是重点

---

# 二、固定结构

最终必须按照以下结构输出：

# Y4测评解读会议记录｜【学生姓名】

## 一、核心结论

提炼 **3–4条最重要的会议结论**。

每一条都应该是一个完整判断，而不是单纯的数据。

重点回答：

1. 学生目前整体处于什么状态？
2. 最大优势是什么？
3. 当前真正的核心问题是什么？
4. 后续成长最应该关注什么？

核心结论应该体现会议中真正形成的判断。

尤其注意区分：

> **"能力不足"**

和

> **"能力很好，但没有被充分发挥/兑现"**

这类关键判断。

---

# 二、心力

围绕Y4"心力"相关内容进行整理。

根据会议实际涉及的内容，可以包含：

### 1. 情绪与自我概念

总结：

* 情绪整体状态
* 情绪稳定性
* 自尊、自信、自我评价
* 对学校表现/自身能力的评价
* 是否存在明显焦虑、无力感等
* 测评与家长反馈是否一致

不要机械按照报告每一个指标逐项复述。

应该提炼出：

> 学生目前的心理状态是什么 → 为什么 → 现实中有什么表现。

### 2. 同伴关系

如果会议涉及：

* 合群
* 朋友
* 社交主动性
* 慢热
* 价值观匹配
* 同伴信任
* 是否存在霸凌/关系冲突

就整理出来。

尤其保留家长对实际社交情况的描述。

### 3. 家庭与依恋关系

如果会议涉及：

* 父母关系
* 家庭沟通
* 信任
* 安全感
* 家长支持
* 学生是否愿意向父母表达

需要重点呈现。

如果家庭是学生的重要优势，要明确指出。

### 4. 内驱力

重点整理：

* 自主性
* 胜任感
* 归属感
* 成长型/固定型思维
* 学生面对困难时的心理状态
* 当前最需要提升的是哪一个部分

特别注意：

如果会议指出"胜任感"是核心问题，要明确写出：

> 为什么胜任感不足 → 会造成什么影响 → 会议建议如何改善。

### 5. 人格

只有在会议实际讨论时才写。

人格部分不要写成心理学科普，也不要评价"好/坏"。

应该关注：

> 学生更倾向于怎样思考、行动、获取能量，以及这种倾向对学习/生活有什么影响。

---

# 三、精力

整理会议中涉及的：

* 睡眠
* 饮食
* 运动
* 身体状态
* 精力管理
* 特殊时期的疲劳/压力

重点判断：

> 精力是不是当前问题？

如果会议认为整体良好，应明确写：

> **目前精力不是主要矛盾。**

不要为了完整而制造问题。

如果会议中提到某个特殊情况（例如考试、备考导致暂时疲劳），需要说明这是阶段性情况，而不是直接定义成长期问题。

---

# 四、学习力

这是Y4会议记录中非常重要的一部分。

建议按照以下逻辑组织：

### 1. 认知资源优势

提炼：

* 整体认知资源
* 注意力
* 记忆
* 推理
* 空间
* 工作记忆
* 意志控制
* 其他会议特别强调的能力

不要变成数据罗列。

应该总结成：

> 学生的底层认知能力处于什么水平，最突出的优势是什么，有没有明显短板。

如果会议明确强调学生的认知资源是核心优势，要突出这一点。

### 2. 执行能力与认知灵活性

整理：

* 执行能力
* 工作记忆
* 意志控制
* 灵活性
* 面对难题时的表现
* 是否容易因为怀疑自己而不敢尝试

尤其关注：

> 学生真正的问题到底是"不会"，还是"因为怀疑自己而没有把能力用出来"。

### 3. 学习动机

重点分析会议中关于：

* 深层动机
* 表面动机
* 学习兴趣
* 学习意义
* 对未来方向的迷茫
* "不知道为什么学习"
* 学习动力不足

的讨论。

如果会议形成了明确判断，例如：

> 学习动机不足并非因为能力不够，而是没有建立学习与未来之间的连接。

必须作为核心结论呈现。

### 4. 学习方法与策略

整理：

* 深层学习方法
* 表层学习方法
* 死记硬背
* 知识总结
* 知识连接
* 思维导图
* 自我调节
* 自主学习

重点回答：

> 学生有没有把自己的认知优势真正转化成学习效率？

### 5. 学习力整体判断

最后用一段话总结：

> 学习力目前最大的优势是什么，真正的短板是什么，以及为什么。

例如：

> "整体来看，学生属于底层认知资源非常优秀，但学习动机和方法尚未充分跟上的状态。"

如果录音中形成了类似判断，应优先保留这种高度概括。

---

# 五、生涯力

整理会议中关于未来方向的讨论。

### 1. 职业/专业兴趣

提炼：

* 学生对什么类型的事情感兴趣
* 更喜欢研究、创造、实践、沟通还是其他活动
* 哪些兴趣与认知优势能够形成匹配

### 2. 能力优势与专业方向

整理：

* 学生自己认为擅长什么
* 测评显示什么能力突出
* 家长认为适合什么方向
* 当前考虑的专业/学科方向
* 能力与专业之间是否存在匹配

### 3. 职业价值观

如果会议讨论了：

* 利他
* 经济回报
* 声望
* 安全稳定
* 社会价值
* 工作环境

等内容，要整理出来。

特别注意区分：

> **学生自己的价值观**

和

> **家庭环境、父母教育可能对其价值观形成的影响。**

如果会议认为需要进一步探索，要明确写出，而不要直接下结论。

### 4. 生涯力整体判断

总结：

> 学生目前有没有明确方向 → 已经出现什么兴趣线索 → 目前最大的探索任务是什么 → 生涯探索如何反过来帮助学习动机。

如果会议中明确提到：

> 专业探索/兴趣探索是建立学习动机的重要路径

需要重点体现。

---

# 六、后续成长重点

根据会议内容提炼 **3–5个优先级明确的成长方向**。

每一个方向必须回答：

**是什么 → 为什么 → 怎么做**

例如：

### 第一优先级：建立胜任感

不要只要求学生达到一个最终目标，而是通过短期、具体、可感知的成功体验，让学生逐渐看到自己的努力能够产生结果，从而修正"我做不好"的自我判断。

### 第二优先级：建立学习与未来的连接

通过专业探索和兴趣探索，让学生逐渐回答"我为什么学习"和"现在学习的东西未来有什么用"，从而推动深层学习动机形成。

注意：以上只是格式示例，**必须根据实际会议内容生成，不得照抄示例。**

---

# 七、会议形成的总体判断

最后用 **1–3段** 对学生进行整体概括。

这一部分不是重复前面的内容，而是把四个"力"串联起来。

重点回答：

> **这个学生现在到底处于什么状态？**

需要尽可能形成一个清晰的"学生画像"。

推荐使用这样的逻辑：

**底层优势 → 当前卡点 → 卡点形成的机制 → 最重要的突破口 → 如果突破之后可能带来的变化**

例如：

> 学生目前并不是能力不足，而是底层能力与实际表现之间存在明显落差。核心问题不是继续证明"他能不能"，而是帮助他建立"我能做到"的体验，并找到值得自己投入的方向。当胜任感、学习动机和学习方法逐渐建立后，现有的认知优势才有机会真正转化为学习表现。

同样，以上只是表达逻辑示例，必须根据本次会议实际内容重新生成。

---

# 三、写作风格要求

## 1. 专业，但不要像心理学报告

这是**Y4解读会议记录**，不是心理测评报告。

应该像专业顾问对学生的会议复盘，而不是把测评报告重新解释一遍。

---

## 2. 有判断，不要只有事实

差的写法：

> "他的自主性比较高，胜任感比较低。"

好的写法：

> "Brian有较强的自主选择意识，但真正的问题在于做出选择之后容易怀疑自己能不能做好，因此当前内驱力中最值得提升的是胜任感。"

---

## 3. 保留家长原话背后的有效信息

不要大量逐字引用家长。

要把家长反馈转化成专业会议记录。

例如家长说：

> "他一直跟我说，在德国没有找到一个真心的朋友。"

可以整理为：

> "家长反馈Brian目前在德国尚未找到自己认为真正交心的朋友，与测评中同伴关系信任与沟通程度相对有限的结果相互印证。"

---

## 4. 强调"交叉验证"

如果同一个结论同时被：

* 测评结果
* 解读老师判断
* 家长现实反馈

三方面支持，要明确体现这种一致性。

这类内容优先级很高。

---

## 5. 不夸大问题

Y4会议记录不能把所有低分都写成"问题"。

必须区分：

* 真正需要关注的问题
* 相对弱项
* 正常范围内的差异
* 学生的个体倾向
* 当前完全没有必要重点关注的部分

如果会议明确认为某个维度"整体OK""没有太多需要关注"，应该直接写出来。

---

## 6. 不要把人格维度写成好坏

人格只是行为和思维倾向。

不要出现：

> "责任心低，所以不好。"

应该写成：

> "责任心相对偏低意味着他可能不适合过度僵化、完全按计划推进的环境，更需要一定的自主空间和灵活性。"

前提是会议中确实有这样的讨论。

---

# 四、信息取舍规则

按照以下优先级处理信息：

**第一优先级：**
会议最终形成的核心判断

**第二优先级：**
家长对学生实际情况的反馈

**第三优先级：**
测评结果与现实情况的交叉验证

**第四优先级：**
老师针对问题提出的具体成长建议

**第五优先级：**
重要的测评数据

**最低优先级：**
单纯重复报告定义、测试原理、没有形成实际判断的数据

---

# 五、禁止事项

不要：

* 自行增加会议没有讨论的建议
* 自行进行新的心理学分析
* 自行判断学生是否存在心理疾病
* 把普通差异写成风险
* 把人格特点写成优劣
* 大量复制测评报告原文
* 大量堆砌分数
* 编造家长没有说过的话
* 编造学生没有表达过的想法
* 为了让四个"力"篇幅均衡而强行添加内容
* 把会议记录写成销售话术
* 把会议记录写成给家长看的鸡汤
* 使用过度夸张的词汇，除非会议原本就明确使用了这些判断

---

# 六、最终输出要求

最终只输出完整的：

# Y4测评解读会议记录｜【学生姓名】

并严格按照：

1. 一、核心结论
2. 二、心力
3. 三、精力
4. 四、学习力
5. 五、生涯力
6. 六、后续成长重点
7. 七、会议形成的总体判断

进行组织。

使用 **Markdown标题 + 小标题 + bullet points + 短段落**。

整体要有明显的document感，避免聊天式表达。

篇幅以**完整但不冗余**为原则：重要内容不能漏，但不要为了增加篇幅重复同一个观点。

最重要的标准是：

> **让一个没有参加这次Y4解读会的顾问，只看这份会议记录，也能准确理解：这个学生目前是什么状态、真正的优势是什么、真正的问题是什么、家长怎么看、测评和现实是否吻合，以及下一步最应该做什么。**

现在请基于我接下来提供的录音转写/会议纪要，直接生成最终会议记录。
